## 请求速率合理性标定（用户请求：多少速率合理）

- 需求：给出「合理的请求速率」的定量标准。
- **核心公式**：合理 rate = 容量点 × 系数；容量点 rate = `min(C_in/L_in, C_out/L_out)`（输入墙与输出墙取小）。
  - `C_in ≈ 8200 in-tok/s`（prefill 墙，实测）；`C_out ≈ 3354 out-tok/s`（per-node decode 墙；PP1 约 2028）。
  - 系数：稳态 0.7~1.0 / 容量点 1.0 / 饱和探针 1.0~2.5；**>2.5× 无信息增益且抬高 retract/崩溃风险**；单流档 << 1× 容量。
- **各画像容量点（本集群）**：chat 512/512 ≈6.5（decode-bound）、code 1K/2K ≈1.6（decode-bound）、standard 4K/2K ≈1.6~2.0（decode/全局）、rag 8K/256 ≈1.0（prefill-bound）、longctx 65K ≈0.125（prefill+KV 池）。
- **关键认知**：并发档的 rate 由「填满并发槽」决定（Little 定律 `在途 = 到达率 × 服务时长`），**不等于 5~10× 容量**；只要 ≈1.2~2× 容量点就能饱和。上一轮把 standard c64/c128/c160 设成 8/12/16（5~10×）属于**过度超配**。

## 业界速率标准的调研结论（用户请求：业界标准的合理值）

- 结论：**业界无「固定 req/s」标准**，标准是「选点方法论」——实测自身 knee 拐点，再按用途取百分比。
- 五个权威依据（已固化进 `reports/PRODUCTION-TEST-PLAN.html` §2.3）：
  - **MLPerf Inference**：Server 场景 = Poisson 到达 + QoS 延迟约束（p99 15~250ms、≤1~3% 违约），指标 = 满足约束的**最大 QPS(λ)**；关键发现 **throughput tax**：Server 吞吐比 Offline 低 **3%~50%** → 饱和吞吐 ≠ 生产可用值。
  - **AWS SageMaker**：以 **knee 拐点**（吞吐持平 + p99 陡升）为安全区上界；提供 `max-concurrency-under-sla` 自动搜索（ttft p95 / tpot p95 / e2e p99 / error rate）。
  - **vLLM / SGLang bench_serving**（DistServe）：`--request-rate` 向上扫描找 SLO frontier，最后一个满足 SLA 的速率 = **goodput**；**默认 `--request-rate inf` 只适合 offline 批量**。
  - **NVIDIA AIPerf / NIM**：**优先用并发**控制负载（原文：用速率时到达率>吞吐会导致未完成请求无限增长）；扫描至略超 max batch size；要求 `ignore_eos=true`。
  - **排队论 / SRE**：`R = S/(1−ρ)`；50%→2×、80%→5×、90%→10×、95%→20×；延迟敏感目标利用率 **60~70%**、批量 **80%**、报警阈值 80%；Little's Law `L = λW`。
- 两条硬规范：**必须开环**（闭环自我节流，压不出 cliff）；**固定输出长度**（`--ignore-eos`）。
- 与本工具对齐：production 族同时设 `max_concurrency` + `request_rate`，恰好符合业界「开环到达 + 并发上限」最佳组合；缺 `--ignore-eos`（`runner.py` 未传）。
- 三层水位：生产稳态 **knee×60~70%**；验收上限 **=knee=goodput**；压力探针 **>knee 到崩溃**。
